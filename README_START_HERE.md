# AKUZ Log Explorer 4.9.0 RC — запуск и настройка

Приложение работает только с файловыми `.log` АКУЗ. Оно получает снимки по SSH с Linux, читает Windows-папку SMB/UNC или заданный локальный .log/каталог, создаёт локальные отчёты и показывает их в браузере. В поставке нет рабочих журналов и демонстрационного отчёта.

## Выбор запуска

**Windows без установки зависимостей:** текущий release candidate имеет версию 4.9.0; до его публикации последний публичный пакет остаётся [v4.8.0](https://github.com/Artemedi/akuzlogparser/releases/tag/v4.8.0). Для проверенного RC используйте собранный portable artifact точного commit SHA, затем запустите `AKUZLogExplorer.exe`. `ConnectConf.cfg` нужно заполнить только для SSH/SMB; для локальных `.log` он не требуется. Python уже внутри. [Подробная инструкция](README_PORTABLE.md).

**Исходники на Windows:** нужен Python 3.9+. Запустите `START_EXPLORER.bat`; для SSH/SMB заранее настройте `ConnectConf.cfg` из `ConnectConf.example.cfg`. BAT устанавливает недостающие runtime-зависимости через `requirements.txt`: Paramiko, а на Python 3.10+ также orjson. Python 3.9 остаётся поддержан и использует stdlib-сериализацию raw-shards.

**Исходники на Linux:** установите `requirements.txt` в виртуальное окружение и выполните `python akuz_app.py --no-browser`. Полные команды — в [README](README.md).

Адрес по умолчанию — `http://127.0.0.1:8765/`. Для остановки нажмите Ctrl+C в консоли приложения. При занятом порте используйте `AKUZLogExplorer.exe --port 8766` либо `python akuz_app.py --port 8766`.

## Linux / SSH

```ini
[ssh]
host = 192.0.2.10
port = 22
compression = false
username = akuz_reader
password =
sudo_password =
key_file =

[logs]
remote_log_dir = /srv/akuz/logs
file_pattern = *.log
local_dest =
base_date =
```

Замените пример адреса и каталога своими значениями.

- До первого подключения проверьте fingerprint сервера и добавьте его ключ в `~/.ssh/known_hosts` текущего пользователя. На Windows это `%USERPROFILE%\.ssh\known_hosts`; можно использовать настроенный Windows OpenSSH. Неизвестный ключ автоматически не принимается.
- `password` — пароль SSH, либо пусто для ключа/агента. `key_file` — путь к закрытому ключу, например `C:\Users\you\.ssh\id_ed25519`.
- `sudo_password` нужен только при чтении через sudo. Пустое значение наследует SSH-пароль; если оба пусты, используется `sudo -n`. Пароль передаётся через stdin, не в тексте удалённой команды.
- Пустой `local_dest` означает `downloads/` рядом с приложением. Относительный путь отсчитывается от папки приложения.
- `base_date` сохранён для совместимости старого конфига; в текущем интерфейсе используются дата выбранного файла или дата из имени.
- Поддерживаются обычные `.log`. Удалённые `.log.gz` не распаковываются. `.jsonl.gz` — отдельный локальный формат входа CLI-генератора.

### Ускоренная загрузка нескольких SSH-журналов в v4.8.0

На Windows portable при выборе **двух и более SSH-журналов** Explorer по
умолчанию предзагружает следующий snapshot отдельным ограниченным процессом,
пока основной процесс разбирает уже скачанный файл. Одновременно работает
не более одного дочернего fetch-процесса.

Оптимизация применяется только к источнику **Linux / SSH** на Windows и не
затрагивает локальные файлы, SMB/UNC или пользовательские генераторы. SSH
compression от неё независима и по-прежнему выключена по умолчанию.

Если нужно немедленно вернуться к последовательному scheduler без изменения
конфига, перед запуском задайте:

```powershell
$env:AKUZ_PHASE11_PROCESS_PREFETCH = '0'
.\AKUZLogExplorer.exe
```

При обычной ошибке предзагрузки приложение возвращается к прежней
последовательной загрузке. Если невозможно доказать безопасное завершение
дочернего процесса/Windows Job Object или корректную очистку owned snapshot,
операция завершается ошибкой вместо запуска второго writer.

На финальной acceptance-матрице до version bump обработка 857,563,363 байт
заняла 329.51 с в последовательном режиме и 277.48 с с process-prefetch
(~15.8% меньше wall); inventory и analytics совпали. Это измерение конкретной
DBA-008D workload, а не обещание фиксированного ускорения на любом сервере.

## Phase 14 — сериализация raw-shards в v4.9.0

На Python 3.10+ и в Windows portable Explorer по умолчанию использует
`orjson` только для массивов строк `data/raw_*.js`. Каталог
`data/catalog.js` продолжает сериализоваться штатным `json.dumps`, поэтому
числовые представления каталога не меняются. На real replicated B/C/C/B/B/C
для 956,307,242 байт median wall снизился примерно на **5.43%**, CPU на
**5.31%**, а measured JSON-время на **50.10%** при полном byte/analytics
parity.

Rollback без изменения конфигурации:

```powershell
$env:AKUZ_PHASE14_RAW_ORJSON = '0'
.\AKUZLogExplorer.exe
```

При Python 3.9 `orjson` не устанавливается и автоматически используется
прежний stdlib encoder; формат отчётов остаётся тем же.

## Windows / SMB / UNC

Приложение должно быть запущено на Windows от пользователя с правом чтения сетевой папки.

```ini
[windows]
enabled = true
log_dir = \\SERVER\AKUZLogs
file_pattern = *.log
local_dest =
```

Выберите **Windows · SMB / UNC** в интерфейсе и нажмите «Список файлов». Используются права текущей учётной записи или заранее подключённые сетевые credentials. WinRM, Windows Event Log и удалённый запуск команд не используются. Предпочтительна отдельная папка с доступом на чтение.

## Локальный файл или каталог

Выберите **«Источник → Локальный .log / папка»**. В появившемся поле введите полный путь на **том компьютере, где запущен Explorer/EXE**, например C:\Vitacore\AIS LPU Server\Logs или D:\AKUZ\20260923_server.log. Путь может указывать на один файл .log либо на папку. Нажмите «Список файлов» (до 30 файлов за пакет) или «Последний лог» (последний по mtime). В папке просматривается только верхний уровень, без рекурсии; другие расширения и символические ссылки не импортируются. Если файлы лежат на сетевой UNC-шаре, используйте источник **Windows · SMB / UNC**.

Локальный источник работает **без SSH, SMB, паролей и настроек ConnectConf.cfg**. Снимок исходного файла копируется в управляемый downloads/ приложения; оригинал не удаляется и не изменяется даже при очистке кэша. Повторное чтение неизменённого снимка использует кэш, выросший .log создаёт новый снимок и отдельный HTML-отчёт. Дата из YYYYMMDD_*.log и ручная корректировка, общая выборка и аналитика работают так же, как с удалёнными журналами. Путь к локальному источнику хранится только в памяти запущенного процесса, не в ConnectConf.cfg; после перезапуска его нужно снова выбрать. Нужны права ОС на чтение файла и запись в каталог приложения. Локальный выбор не импортирует Windows Event Log или другие системные журналы.

## Выбор журналов и даты

1. Нажмите «Список файлов».
2. Выберите до 30 файлов. Фильтры списка «с/по» относятся к дате изменения файла (`mtime`), а не к датам событий.
3. Проверьте дату первой записи рядом с каждым файлом. Из имени `20260923_*.log` автоматически подставляется **23.09.2026**. Ручная дата имеет приоритет.
4. Нажмите «Создать отчёты по выбранным файлам» и дождитесь завершения всей операции.
5. Откройте отдельный отчёт, общую выборку или аналитику ошибок.

Дата первой записи нужна потому, что записи АКУЗ могут содержать только время `HH:mm:ss.fff`. Переходы через полночь увеличивают день. Если имя не содержит корректной даты и поле пустое, отчёт показывает `D+0`, `D+1`; для такой пачки общая календарная выборка не создаётся. Поэтому появляется предупреждение о недостающей дате.

Кнопка «Последний лог» выбирает файл с наиболее поздним mtime; дату событий всё равно берёт из имени, а не из mtime. Несколько файлов одного дня остаются независимыми источниками.

Список можно свернуть вручную; после успешной обработки он сворачивается автоматически. При ошибке остаётся доступным.

## Повторный выбор и растущие файлы

Перед использованием кэша приложение перечитывает размеры и метаданные выбранного источника. Неизменённый снимок с той же датой переиспользуется. Если файл вырос, **по умолчанию** сохраняется прежнее безопасное поведение:
скачивается новый bounded snapshot целиком, а старый отчёт остаётся доступен.
Экспериментально проверенный Phase 12 delta/resume можно включить только явно
для Linux/SSH:

```powershell
$env:AKUZ_PHASE12_DELTA_RESUME = '1'
.\AKUZLogExplorer.exe
```

Первый opt-in snapshot только сохраняет proof metadata. При следующем росте
того же host/path/device/inode Explorer может скачать лишь append, но принимает
результат только после полного SHA-256 удалённого принятого префикса и локальной
сборки. Старый кэш без proof metadata не угадывается. При обычной ошибке
доказательства/передачи выполняется свежая полная bounded-загрузка; при
небезопасной коллизии публикация остаётся fail-closed. Resume начинается с
фактически сохранённых `stored_bytes`, поэтому отброшенный незавершённый хвост
активного файла не считается принятым.

Пока Phase 12 включён, Phase 11 process-prefetch намеренно отключается: совместная
работа двух оптимизаций требует отдельного gate. Сбросьте переменную или задайте
`AKUZ_PHASE12_DELTA_RESUME=0`, чтобы вернуться к обычному v4.9 пути.

Встроенная SSH-компрессия остаётся независимой, выключена по умолчанию и
включается только явно через `[ssh] compression = true` с учётом дополнительной
CPU-нагрузки на сервер.

Идентификатор снимка учитывает сервер, путь, размер, mtime и доступный идентификатор файла. Локальная копия проверяется по размеру и SHA-256. Это не удалённое побайтовое сравнение: перезапись при неизменных размере и mtime может остаться незамеченной.

### Необязательная полная перепроверка исходного локального .log

Если важно обнаруживать перезапись **исходного локального журнала** при
сохранённых размере, `mtime` и inode/file ID, можно включить полный SHA-256
перед повторным использованием отчёта. Для portable v4.9.0:

```powershell
$env:AKUZ_VERIFY_LOCAL_SOURCE_SHA = '1'
.\AKUZLogExplorer.exe
```

Для запуска из исходников вместо EXE используйте
`python akuz_app.py --no-browser`.

Задавайте переменную **до запуска процесса** Explorer. Значения
`1`/`true`/`yes`/`on` включают проверку; `0`/`false`/`no`/`off`
и отсутствие переменной отключают её; неверное значение для
локального источника вызывает ошибку вместо молчаливого отключения.
По умолчанию режим выключен. Список и дата обновляются обычным
способом, но для индексированного источника дополнительно
пересчитывается **весь** SHA исходного файла, а не хеш начала или
конца, и сравнивается с SHA сохранённого снимка/отчёта. Эта
перепроверка не переписывает журнал, отчёт, конфиг или кэш.

При несовпадении прежний отчёт не выдаётся как актуальный, но
исторические отчёты остаются на месте; обновите источник с новым
временем изменения или именем, чтобы создать новую идентичность,
не удаляя старые отчёты. Если файл меняется во время чтения,
операция прекращается. Дополнительный проход по всему исходнику
может дорого стоить на журналах в сотни гигабайт; не считайте
режим ускорением или полноценной защитой от параллельной записи
после проверки. Для SSH/SMB эта опция **не действует**. В portable v4.7.0 режим входит,
но остаётся выключенным по умолчанию; задавайте переменную среды до запуска
EXE и закрывайте прежний экземпляр перед повторным стартом.


Перед чтением активного файла фиксируется граница байтов. Дописывание после неё допускается. Недописанная последняя физическая строка активного снимка отбрасывается только локально. У завершённого неизменного файла отсутствие последнего перевода строки допускается. При обнаруженной замене файла, усечении или неполной передаче снимок отклоняется.

Исходный файл не изменяется; удалённые архивы и временные файлы не создаются. Снимок не является транзакционным: изменения внутри уже записанного диапазона не всегда обнаружимы.

## Отчёты, аналитика и очистка

Отчёты сохраняются в `reports/`; «Мои отчёты» показывает зарегистрированную библиотеку. При наличии дат всех выбранных источников дополнительно создаётся общая выборка. Разные пути или серверы не объединяются только из-за одинакового содержимого.

Аналитика использует обработанные отчёты, а не скачивает логи повторно. До окончания всей пачки и обновления индекса её открытие заблокировано в интерфейсе и на сервере. Старые отчёты без даты получают её из имени `YYYYMMDD_*.log`; исправить дату можно в панели источников. Старый HTML-отчёт при этом не переписывается. [Методика](README_ANALYTICS.md).

«Очистить кэш» после подтверждения удаляет **только зарегистрированные скачанные копии `akuz_v4_*`**. Готовые HTML-отчёты в `reports/` и их аналитические данные сохраняются; отдельной галочки удаления отчётов в v4.5.0 больше нет. Исходные файлы выбранного источника (в том числе локальные) и посторонние файлы не затрагиваются. После очистки повторная загрузка исходного `.log` может потребоваться для создания нового отчёта.

## Обновление и перенос

Закройте приложение. При portable-обновлении замените только EXE; при обновлении исходников — код и интерфейс. Сохраните `ConnectConf.cfg`, `reports/`, `cache/`, `downloads/`, `data/`. Не заменяйте заполненный конфиг примером из ZIP.

При открытии аналитики индекс схемы 5 обновляется автоматически; исправлена миграция старой таблицы без `relative_day`. Для переноса всей библиотеки копируйте папку приложения целиком. Отдельный отчёт переносится со своим `data/`, но общая аналитика требует корневой библиотеки и инвентаря.

**Важно:** EXE обновляет интерфейс в корне приложения при запуске, но уже созданные каталоги `reports/v4_*/` остаются неизменными. Чтобы обновить их почасовой график и оформление, используйте `scripts/refresh_report_ui.py` из исходников: без флага — просмотр списка, с `--apply` — обновление только HTML/JS/CSS. Остановите приложение на время операции. [Команды и ограничения](README_EXPLORER.md#обновление-уже-созданных-отчётов).

## Диагностика медленной обработки

В **v4.7.0** запустите интересующую операцию в Explorer, затем откройте `<папка_с_EXE>/diagnostics/performance.txt` (для запуска исходников — `diagnostics/` в корне проекта). Файл содержит локальную дату/время с часовым поясом, `stage`, `status` и числовые показатели; отдельные этапы получают `elapsed_s`. При разборе, объединении и индексации крупных отчётов пишется `status=progress` каждые 50 000 событий. Резервные файлы: `performance.txt.1` и `.2`, ротация при размере от 3 МиБ. Если этап начал выполняться, но не завершился, найдите последнее `start`/`progress`: отсутствие `done` само по себе не доказывает сбой — операция могла ещё продолжаться или процесс был остановлен.

| `stage` | Что измеряется / как интерпретировать |
| --- | --- |
| `source.fetch` | Получение источника целиком; `source_kind`: 1 = Linux/SSH, 2 = Windows/SMB, 3 = локальный файл. Не суммируйте с вложенными `source.ssh.*` |
| `report.generate` | Вся генерация одного отчёта; вложенные фазы учитываются в её длительности, **не складывайте их повторно** |
| `generate.parse` | Чтение событий, текстовая классификация, подготовка каталога и запись `raw_*.js`; `shard_write_s` показывает суммарное время записи частей |
| `generate.catalog` | Сериализация и запись большого `data/catalog.js` |
| `combined.stream` | В v4.7.0: поток объединённых событий **внутри** `report.generate`; старый `combined.merge` с промежуточным JSONL сохранён для CLI/пользовательского генератора |
| `analytics.refresh` | Полный цикл индекса ошибок, в том числе `analytics.inventory`, `analytics.ingest`, `analytics.export`, `analytics.overview` |
| `worker.perform_build_current` | Полная операция, в том числе загрузка отдельных отчётов, общая выборка и аналитика |

В v4.7.0 SSH дополнительно пишет `source.ssh.connect` (включая `compression=0/1`), `source.ssh.inventory`, `source.ssh.stat_before`, `source.ssh.transfer`, `source.ssh.stat_after`, а при усечении активного снимка — `source.ssh.trim_rehash`. Прогресс передачи — каждые 64 МиБ с числовыми полями `bytes_received`, `bytes_expected`, `elapsed_s`, `mib_per_s`. Это вложенные этапы внутри `source.fetch`, их не следует прибавлять повторно. Для локальных и Windows/SMB-снимков SHA-256 теперь считается во время копирования; второй проход по диску нужен только при фактическом усечении незавершённой строки.

Для сравнения производительности используйте `elapsed_s`, `input_bytes` / `bytes_saved` и число `events` в рамках **одной операции**. Не суммируйте вложенные интервалы и не сопоставляйте необоснованно полный и неполный журналы. Если тормозит `generate.parse` при малом `shard_write_s`, вероятна работа в памяти/CPU; если `generate.catalog` или `analytics.export` — важна сериализация и запись; если `source.fetch` — источник/сеть/диск. Это ориентиры для следующего исследования, не автоматическое определение причины.

Диагностика не содержит текста исходных событий, имён пациентов, путей журналов и паролей; логирует только предусмотренные кодом названия этапов и числовые метрики. Тем не менее перед передачей файла проверьте его содержимое и соблюдайте локальные правила работы с данными. **Отладочный журнал не ускоряет парсер сам по себе**, но помогает адресно выбрать оптимизацию. Аналитика и отчёты из предыдущих запусков задним числом не профилируются.

### Проверка SSH-компрессии

В новой локальной версии предусмотрен **необязательный** переключатель в собственной секции `[ssh]` файла `ConnectConf.cfg`:

```ini
compression = false
```

По умолчанию он выключен (включая старые конфиги без этого ключа). В Phase 10 выполнены три реальные balanced A/B серии по 3 прогона на режим для журналов 140–645 МБ. На этих данных `compression=true` уменьшал медианное время SSH-передачи примерно на **67,6–71,0%**, а количество байт, полученных клиентским socket, на **72,1–76,9%**. При этом измеренный CPU родительского процесса `sshd` на сервере вырос примерно в **5,2–6,1 раза**; на самом крупном префиксе — с 2,72 до 16,59 CPU-секунд при 19,27 с wall time.

Поэтому default остаётся `false`. Включайте `true` как opt-in, когда диагностика показывает, что основной резерв — `source.ssh.transfer`, и на сервере приложений есть подтверждённый запас CPU. Не включайте компрессию автоматически только из-за размера файла и не проводите тест с искусственным сбросом page cache на production-сервере. Для собственной проверки сравнивайте `source.ssh.transfer elapsed_s` / `mib_per_s`, размер источника и системную загрузку. Значение влияет только на SSH-сеанс, не меняет формат отчёта и не включает компрессию для SMB/локального источника. Для уже скачанного снимка повторное получение не произойдёт из-за кэша — учитывайте это при A/B. Полные условия и измерения: `PHASE10_SSH_COMPRESSION.md`.

## Доступ и диагностика

Сервис слушает только `127.0.0.1`, проверяет Host/Origin и не выдаёт конфиг, `.log`, инвентарь и Python-код. Интерфейс не использует CDN. Конфиг с паролями и отчёты могут содержать чувствительные данные — храните папку с подходящими правами доступа.

- **Нет файлов:** проверьте выбранный источник, абсолютный путь, расширение и маску `*.log` и права чтения.
- **Неизвестный SSH-ключ:** проверьте fingerprint и настройте known_hosts текущего пользователя.
- **Файл ротирован/усечён:** обновите список и повторите операцию.
- **Занят порт:** закройте предыдущий экземпляр или задайте другой порт.
- **Нет календарного графика:** проверьте имя и дату источника, а также сообщения о конфликтах в аналитике.
- **Ошибка старого индекса:** обновите приложение и перезапустите его; удалять отчёты не нужно.
- **Разбор очень долгий:** проверьте последнее событие в `diagnostics/performance.txt`, сравните `generate.parse`, `generate.catalog`, `combined.stream` и `analytics.ingest`; при необходимости передайте этот диагностический файл после проверки содержимого.

Проверки сборки используют синтетические журналы, локальный HTTP, локальный .log и моделирование SSH/SMB. Они не заменяют проверку подключения к вашему рабочему SSH-серверу или SMB-папке.

### Сравнение старого и нового EXE

v4.5.0 не содержит нового find-классификатора, v4.7.0 содержит. Неизменённый источник может переиспользоваться из кэша; для полного замера нужен новый/изменившийся снимок. SSH-передача и генерация измеряются отдельно. Синтетическое ускорение не является обещанием для рабочего файла.
