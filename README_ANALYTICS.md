# AKUZ Log Explorer 4.6.0 — аналитика ошибок

Аналитика читает только уже обработанные и зарегистрированные файловые журналы приложения АКУЗ, включая локальные .log. Системные журналы, Windows Event Log, PostgreSQL и исходники VCLib не анализируются.

## Использование

1. Создайте отчёты через приложение и дождитесь окончания всей пачки. Во время загрузки, обработки и обновления индекса открытие аналитики заблокировано, включая прямые HTTP-запросы.
2. Откройте «Аналитика ошибок» на главной странице или из отчёта.
3. Выберите способ группировки, семейство или введите текст поиска.
4. Нажмите группу: откроются график по дням/часам и таблица появлений.
5. Нажмите столбец графика для фильтра интервала или номер события для перехода к исходному тексту.

## Группировка

| Режим | Что объединяется |
| --- | --- |
| По типу ошибки, по умолчанию | Класс исключения в пределах семейства |
| По точному шаблону | Тип + нормализованное сообщение + первый распознанный кадр стека |
| По семейству | Все распознанные ошибки сериализации либо остальные ошибки |

Нормализация маскирует GUID, IP, email, HEX и числовые значения в шаблоне. Разные точные шаблоны могут входить в один тип или семейство. Совпадение группы не доказывает общую причину сбоя. Исходный полный текст остаётся в отчёте.

## Календарь и относительное время

По принятой схеме `20260923_*.log` означает дату первой записи 2026-09-23. Она определяется автоматически, включая старые отчёты без назначенной даты. Ручная дата имеет приоритет. К дате прибавляется смещение дня внутри конкретного источника; переход через полночь учитывается.

Время изменения файла (`mtime`) не используется как дата события. Если имя не соответствует маске или содержит невозможную дату, укажите дату вручную либо используйте относительную шкалу `D+0`, `D+1` и часы журнала. Относительные дни разных файлов не означают один календарный день.

Панель «Календарные даты исходных журналов» позволяет исправить дату без повторной загрузки `.log`. Изменяются метаданные и аналитический индекс; исходные события и старый HTML-отчёт не переписываются. Изменение даты требует работающего локального сервиса, офлайн-просмотр — нет.

## Дедупликация и конфликты

Повторные снимки одного источника сопоставляются по серверу, пути, дате, исходным строкам и хешу записи. Совпадающее событие не должно повторно учитываться только из-за наличия отдельного и объединённого отчёта.

Одинакового SHA-256 недостаточно для объединения независимых серверов или путей. Старые отчёты без сохранённого имени сервера не позволяют уверенно различить такие источники; при необходимости их нужно пересоздать.

Если начало строки совпадает, а исходный текст различается, события помечаются как неопределённые: сохраняются в таблице и количестве, но исключаются из временных графиков. При разных датах одного и того же байтово идентичного источника фиксируется конфликт дат, календарный график для него не строится.

Это консервативное сопоставление: переиспользование пути после ротации может потребовать ручного разделения источников. Синхронизация часов нескольких серверов не проверяется. Дедупликация аналитики не равна побайтовому вычитанию префикса файлов в обычной общей выборке.

## Индекс и офлайн-снимок

Источники регистрируются в `cache/inventory.json`; события читаются из `reports/<id>/data/catalog.js` и `raw_*.js`. Аналитика не скачивает оригинальные `.log` и не подключается к серверу.

| Файл | Назначение |
| --- | --- |
| `cache/error_analytics.sqlite` | Перестраиваемый индекс, схема 5 |
| `data/analytics.js` | Сводка и список групп |
| `data/error_<id>.js` | Детали точного шаблона |
| `data/type_<id>.js` | Детали типа |
| `data/family_<id>.js` | Детали семейства |

Индекс обновляется после обработки пачки и при открытии аналитики через сервис. В v4.5.0 эти действия отмечаются в `diagnostics/performance.txt`: `analytics.inventory`, `analytics.ingest`, `analytics.export`, `analytics.overview` внутри `analytics.refresh`. Для долгого индексирования проверяйте время и отметки прогресса каждые 50 000 событий. Подробности — в [диагностике](README_START_HERE.md#диагностика-медленной-обработки). Исправлена миграция таблиц без `relative_day`, в том числе если старый индекс ошибочно помечен новой версией. Сохранённые отчёты при миграции не удаляются.

После формирования снимка `errors.html` открывается через `file://`. Сохраняйте структуру корневых `data/` и `reports/`. Отдельно созданный CLI-отчёт или скопированная чужая папка автоматически в библиотеку не импортируются.

## Ограничения

Распознавание основано на классах исключений и текстовых признаках; возможны ложные совпадения и пропуски. В исходных логах может не быть уровней ERROR/INFO/WARN. Большая библиотека требует времени и памяти для индексации и статического экспорта.

Тексты, названия источников и SQLite могут содержать чувствительные сведения. Всё вычисляется локально, без CDN, внешней аналитики или AI-сервисов. Проверки используют синтетические журналы, не рабочие медицинские данные.

### Совместимость аналитики v4.6.0

Оптимизация касается скорости классификации сообщений при генерации, а не алгоритма отпечатков ошибок: `recognize_error()` и SHA-256-префикс fingerprint не заменены. Схема SQLite осталась 5; исходные `reports/` и заполненный `ConnectConf.cfg` сохраняются при обновлении EXE. Динамика ошибок и `analytics.ingest` измеряются отдельно от генерации и SSH-передачи.
