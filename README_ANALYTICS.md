# AKUZ Log Explorer v4.2 — Аналитика ошибок

Самостоятельный проект akuzlogparser. Источники — исключительно файловые .log приложения
AKUZ из настроенного каталога Linux/SSH или Windows/SMB. Windows Event Log,
журналы PostgreSQL/Linux и исходники VCLib не собираются и не анализируются.

## Использование

1. Создайте отчёт из одного или нескольких файлов AKUZ через обычный Explorer.
2. Откройте «▥ Аналитика ошибок» на главной странице или в отчёте.
3. Поиск групп — по типу исключения, нормализованному сообщению или первому
   кадру stack trace. Семейство «Сериализация» — отдельный фильтр.
4. Нажмите на группу: график по дням/часам; даты С/По; нажатие на столбец
   ограничивает таблицу исходных событий соответствующим интервалом.
5. В таблице «#номер» открывает конкретное событие соответствующего отчёта
   в новой вкладке. Из новой карточки распознанной ошибки есть обратная ссылка
   на аналитику этой ошибки.

## Что индексируется

Только сохранённые в cache/inventory.json HTML-отчёты с полным текстом исходных
AKUZ-событий в reports/<report_id>/data/raw_*.js. Загрузка оригинального .log
или повторное обращение к серверу для построения аналитики не требуется.
При открытии /errors.html на локальном HTTP-сервисе индекс автоматически
обновляется. При создании нового отчёта он обновляется в конце операции.

cache/error_analytics.sqlite — производный, удаляемый и перестраиваемый индекс.
data/analytics.js и data/error_<fingerprint>.js — статический снимок аналитики.
После его генерации errors.html работает по file:// без сервера и сети,
при сохранённой структуре каталогов проекта (включая reports/ и data/).
Отдельно скопированный HTML-отчёт сохраняет просмотр журнала, но для
аналитики *всей библиотеки* должен иметь доступ к корню проекта.

## Принцип группировки

Точное совпадение: тип исключения + нормализованное сообщение + первый
распознанный stack frame (если он есть). GUID, IP, email, HEX и числовые значения
маскируются в шаблоне. Ошибки с разными точными fingerprints могут быть
показаны рядом через «Семейство» или текстовый поиск. Текстовые шаблоны
не являются установленной причиной исключения.

Повторные снимки одного источника с совпадающими host, origin path,
датой первой записи, номером исходной строки и полным hash записи
учитываются один раз.
Идентичный SHA-256 сам по себе не достаточен: независимые серверы или
пути могут содержать одинаковые байты при разных реальных событиях.
Начиная с индекса v3 сопоставление точных файлов учитывает также сервер
и исходный путь, а совпадение начала растущего файла проверяется по
исходной позиции строки и полному хешу записи в рамках того же источника.
Старые отчёты без сохранённого host не позволяют уверенно различить
серверы с одним и тем же путём; при необходимости их следует пересоздать
с актуальной версией генератора.
Совпадающее начало строки при различном raw_hash считается конфликтом:
события видны в таблице и общем количестве с отметкой «неопределённо»,
но исключены из календарной диаграммы. Это консервативная защита: разные
реальные файлы, переиспользующие тот же путь в один день, могут потребовать
ручного разделения источников; автоматического доказательства непрерывности
после ротации по имени файла нет.

При разных датах первой записи одного и того же байтово идентичного файла
индекс отмечает конфликт дат, не выбирает дату автоматически и исключает
этот источник из календарного графика.

Календарная дата выводится из *подтверждённой оператором* даты первой записи
и day_offset в отчёте. Предложенная интерфейсом дата по mtime не считается
подтверждением без проверки пользователем. Если дата не задана,
событие присутствует в списке и общей статистике, но не на диаграмме
по дням или календарным часам.

## Конфиденциальность и ограничения

Статические files/SQLite могут содержать фрагменты исходных сообщений и
имена источников: обращайтесь с ними как с журналами с ПДн/медданными.
Все вычисления локальные, нет CDN, облачных сервисов, AI-диагностики или
сетевых запросов помимо явно настроенного скачивания .log.
Дедупликация ограничена обработанными отчётами из одной библиотеки;
не импортирует чужие старые папки, не включённые в inventory.json.
Временные шкалы нескольких серверов не доказывают синхронизацию их часов.
Источник не имеет уровня ERROR/INFO/WARN: тип ошибки определяется
по текстовым признакам и классу исключения, возможны ложные совпадения.

## Подтверждение даты в интерфейсе

Начиная с этой доработки поле «Дата первой записи» намеренно пустое даже при
наличии подсказки mtime. Пользователь указывает дату самостоятельно; иначе
события сохраняются в таблице без календарной даты и не участвуют в графиках.
Ранее сформированные отчёты могут содержать даты, автоматически предложенные
старым интерфейсом. При интерпретации старых графиков требуется проверить
происхождение этой даты — старые данные не позволяют доказать факт проверки.
